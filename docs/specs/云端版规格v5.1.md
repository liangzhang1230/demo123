# §0 本文件是什么（先读这一页，否则全文读不懂）

## 0.1 三句话

1. **v4.0 的业务层已被五个板块整体取代。** v4.0 写于五板块之前，其 M1–M19 的公式、口径、话术、对拍常量，现在全部有更新更严的版本。本文件**不复述**它们。
2. **本文件只负责一件事：把五板块的单机能力，架到云上多租户跑起来。** 业务口径一个字不改、不改写、不"优化"。
3. **因此本文件不可单独交付开发。** 它是七份文件里的第七份。单独给 AI，AI 会因为找不到公式而开始编——那正是这套架构要杜绝的。

## 0.2 引用锁（Reference Lock）——本文件的唯一写作纪律

每个业务模块只写三样东西：

```
【口径出处】 🔒 指向某板块某条，逐字生效，本文件不复述、不摘录、不改写、不"总结"
【处置】     该模块相对 v4.0 的命运：🔴取代 / 🟡改造保留 / 🟢云端新增 / ⬛删除
【云端增量】 只有这一列是本文件的原创内容，也是唯一需要长期维护的东西
```

🔴 **铁律 L-1**：本文件出现的任何业务数字（阈值、系数、公式、对拍值），若与被引用板块不一致，**一律以板块为准，本文件视为笔误**。
🔴 **铁律 L-2**：板块升级 → 本文件**自动跟随**，无需改动，除非改的是"云端增量"列。
🔴 **铁律 L-3**：本文件**不得**新增任何业务口径。如果云端确实需要一条五板块没有的业务规则，**回去改板块规格**，不要在这里加——那会立刻制造第二个事实源。

## 0.3 两个版本的产品分界（这也是定价分界）

| | 单机版（五板块 HTML） | 云端版（本文件） |
|---|---|---|
| 一句话 | **老板一个人的分析工具**：我算给我自己看 | **全公司在跑的运营系统**：所有人每天在里面工作 |
| 用户 | 老板本人（+ 财务/HR 录入） | 老板 / 高管 / 主管 / 招聘者 / 销售，全员 |
| 数据 | 老板手动录入或导入 | 销售每天自己填，事件流自动流转 |
| 交付 | 单 HTML，双击即用，数据不出本机 | 多租户 SaaS，浏览器登录 |
| 联动 | 手动导出/导入信封 JSON | 同库直连，实时 |
| 有而云端没有的 | — | — |
| 云端有而单机没有的 | — | 销售端填报、钱途页、悬赏栏、早报推送、白话原语、多角色权限、订阅计费 |

🔴 **不刻意阉割单机版。** 分界是天然的：单机版做不了"多人每天在里面工作"，因为它没有多人。这条分界即定价理由，无需人为制造差异。

# §2 总体架构

## 2.1 分层（🔴 云端版的核心结构）

```
┌─────────────────────────────────────────────────────────┐
│ L4 表现层   销售端 / 主管端 / 招聘者端 / 老板端 / 平台驾驶舱      │ ← 云端原创
├─────────────────────────────────────────────────────────┤
│ L3 推送层   插卡总线 / 早报 / 播报 / action_card 状态机        │ ← 云端原创
├─────────────────────────────────────────────────────────┤
│ L2 业务层   五板块全部口径（🔒 引用锁，本文件零复述）              │ ← 五板块权威
│            dingjia · zhaoren · suanzhang · liuren · yuren │
├─────────────────────────────────────────────────────────┤
│ L1 底座层   多租户 / 登录 / 权限 / 事件流 / 日切 / 商业化 / 支付   │ ← 云端原创
└─────────────────────────────────────────────────────────┘
```

🔴 **L2 是只读引用层**：云端**不重新实现**任何业务公式，而是把五板块的纯函数库（`src/domain/{board}/`）**原样移植**为服务端模块。移植 = 复制代码 + 加 `tenantId` 参数，**不改逻辑**。
🔴 **L2 的自测报告必须能跑通五板块各自的全部对拍**（定价器 25 条 / 招人器 24 条 / 算账器 **22** 条 / 留人器 **19** 条 / 育人器 **19** 条，**合计 109 条**——🔧V-14 原文"105/108"两数并存且各板块条数过期，已按现行件七逐份清点统一）。**109 条全绿 = L2 移植合格**，一条不绿即视为改了口径。

## 2.2 单机 ⇄ 云端的关系

```
单机版信封（公约【7】skab_v1）
     ↓ 导入
云端：一次性迁移工具（老板把 5 个 HTML 的信封上传 → 落入本租户库）
     ↑ 导出
云端：随时导出为同一信封格式 → 可回落单机版
```

🔴 **双向可迁移是承诺，不是可选项**（见 §9 A-C05）。理由：老板买单机版在先，云端版必须能接住他攒的数据；云端版停用后数据必须能带走。**不锁客户，是这套产品的人设。**

## 2.3 数据流
🔒 **口径出处**：《0号公约》【7.2】字段级互锁表（20 行）。
**云端增量**：单机版靠"导出信封 → 导入"传递的 20 个字段，云端**全部变为同库直读**——`ExternalRef` 与信封新鲜度规则（公约 §7.3）在云端**降级为非必需**（数据实时，`staleDays` 恒为 0）。
🔴 但 **`derived` 派生标量仍须落表**（不可每次现算），并保留 `computedAt` 字段——公约 A-21"带来源与 asOf"在云端依然生效，只是 asOf 从"导出日"变为"计算日"。
